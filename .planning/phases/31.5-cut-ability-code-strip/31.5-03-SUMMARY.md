## Decisions Made

- **Atomic commit boundary widened from 6 files to 7:** the canonical atomic-commit unit per CONTEXT D-15 + RESEARCH Pattern 1 is "schema + 5 presets in one commit." Discovered during Task 3 boot-smoke gate that `main.py:118` imports `BOOST_DOWNWARD_DAMAGE_W, BOOST_DOWNWARD_DAMAGE_H` from `src.core.constants`, which is a wildcard re-export from `src.core.tuning.__all__`. Splitting the main.py fix into a separate commit would create the exact bisect window CONTEXT D-15 exists to prevent. Resolved by folding into the atomic commit (Rule 3 — see Deviations).

- **Did NOT touch `derived.*` block in physics-schema.json:** the `derived.player`, `derived.jump`, `derived.fall`, `derived.clearance`, `derived.placement_rules` blocks reference no cut keys — they are computed Euler-integration outputs for the pml-to-ldtk converter. Out of scope.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Removed BOOST_DOWNWARD_DAMAGE_W/H from main.py and deleted the dead BOOSTING boost-stomp-damage block**

- **Found during:** Task 3 (boot smoke gate)
- **Issue:** After the schema strip removed the `boost` group from `physics-schema.json`, the `tuning._flat_index` rebuild dropped `BOOST_DOWNWARD_DAMAGE_W/H`. `src.core.constants` is a compat shim that does `from src.core.tuning import *` (wildcard re-export of `tuning.__all__`), so those names also vanished from `constants`. `main.py:118` had `from src.core.constants import (BOOST_DOWNWARD_DAMAGE_W, BOOST_DOWNWARD_DAMAGE_H, ...)` which raised `ImportError: cannot import name 'BOOST_DOWNWARD_DAMAGE_W' from 'src.core.constants'` at module-load time. Boot-smoke gate failed with rc=0 (immediate ImportError, not timeout). The names were used only in the dead `if self.player.state == "BOOSTING":` block at lines 726-745, which is unreachable after Plan 01 (BOOSTING state name removed; never set anywhere).
- **Why this wasn't caught earlier:** Plan 04 (Wave-2 sibling) covers the cross-cutting infrastructure strip (input + save + items + main.py LDtk loader + entity-schema + UI) but its task descriptions do NOT enumerate the boost-stomp-damage block in main.py. RESEARCH Risk Surface 1 ("dead-reference window") flagged `tuning.DASH_IFRAMES` as an awareness-only window between Plan 01 method delete and Plan 03 schema strip, but did not flag `BOOST_DOWNWARD_DAMAGE_W/H` because it lives in main.py (not player.py) and its containing block was technically not "deleted in Plan 01" — it was made unreachable but the import wiring remained.
- **Fix:** (a) Removed `BOOST_DOWNWARD_DAMAGE_W, BOOST_DOWNWARD_DAMAGE_H` from the multi-name import statement at main.py:118; (b) deleted the entire `if self.player.state == "BOOSTING": ... # Slime Boost enemy stomp damage (D-10)` block (was 20 lines). The block was already dead code post-Plan-01 (state never sets BOOSTING).
- **Files modified:** `main.py` (folded into the same commit per CONTEXT D-15 atomicity rationale).
- **Verification:** `timeout 5 python main.py` now returns rc=124 (clean boot timeout, not a crash). `grep -nE 'BOOST_DOWNWARD_DAMAGE' main.py` returns 0 matches. `grep -n '"BOOSTING"' main.py` returns 0 matches.
- **Committed in:** `1c66193` (the atomic Plan 03 commit).
- **Scope note:** This fix is in `main.py`, which is technically a Plan 04 file. The Plan 04 plan does not list this specific edit but its task description for main.py says "delete cut-pickup `elif` branches from LDtk loader" — the boost-stomp block is a separate region. The orchestrator merging Plan 04's worktree alongside Plan 03's will see this fix already landed; Plan 04's main.py edit (LDtk loader branches) is at a different region (lines 442-455) and will not conflict.
