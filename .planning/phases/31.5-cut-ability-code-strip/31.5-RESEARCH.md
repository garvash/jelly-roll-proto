## Architecture Patterns

### Pattern 1: Atomic schema-and-preset rewrite

**What:** Schema (`physics-schema.json`) and the 5 preset JSON files form a single coherent meaning ("the cut groups don't exist"). The schema defines what `_flat_index` knows; presets supply values. If schema lands without presets being updated, `presets.py` walks `_flat_index` keys, presets contain extra cut keys, `set_value(key, val)` raises `KeyError`. The forward-compat skip at lines 84-88 silently swallows it, but the bisect window between schema commit and preset commit would have unpredictable game state.

**When to use:** Always for cross-file data-shape changes.

**Example:**
```bash
# Plan 03 commit boundary:
git add assets/physics-schema.json \
        assets/presets/_v1.3-reference.json \
        assets/presets/slot_0.json \
        assets/presets/slot_1.json \
        assets/presets/slot_2.json \
        assets/presets/slot_3.json
git commit -m "feat(31.5): strip cut-ability tuning groups + preset values"
```

Source: CONTEXT D-15 + Specifics line 221.

### Pattern 2: Top-down by symbol within a single large file (D-17)

**What:** Strip largest entity-monolith (`player.py`, 915 LOC) by deleting one method-pair / state-branch at a time, top-down by line. Verify import + boot after each sub-step. The 6 sub-steps in D-17 (ram → boost → dash → bubble shield → charge shot → flag init) are independently rollbackable WITHIN Plan 01.

**When to use:** When a file has multiple logically-independent strip targets that are textually intermingled.

**Invariant:** After each sub-step, `python -c "import src.entities.player"` must succeed (no `NameError` from a half-stripped reference). After sub-steps 1-4, `python main.py` must boot to title screen. Sub-step 5 (charge shot input branches) and sub-step 6 (flag init) are the last; their breaking would prevent the Plan 01 commit anyway.

Source: CONTEXT D-17, formalized in Sequence Verification below.

### Pattern 3: Defensive `getattr(player, "has_X", False)` reads (preserved)

**What:** `save_manager.py:34` reads `has_drill` via `getattr(player, "has_drill", False)`. Same pattern previously used for cut flags. After strip, only the drill `getattr` survives. The pattern itself stays untouched.

**Why preserved:** Forward-compat against future flag additions/removals. Phase 32 will repeat this pattern when adding new flags for FusionAbility Protocol state.

Source: PATTERNS Shared Patterns section.

### Pattern 4: Per-test-file `make_player(**overrides)` helper

**What:** Each test file defines its own `make_player(**overrides)` helper that constructs a Player instance and applies arbitrary kwargs via `setattr`. After strip, `make_player(has_dash=False)` calls in mixed-test files would set an attribute that doesn't exist — but `setattr` on Python objects creates new attributes silently, so it WOULD NOT raise. **The risk is the inverse:** the test would set `has_dash=False` on a stripped Player, then assert downstream behavior that depends on the attribute being read by player methods. Since the methods that read it are gone, the kwarg becomes a no-op and the assertion either trivially passes or fails for an unrelated reason.

**When to use:** Recognize this in Plan 05. Drop dead kwargs from the 6 mixed-test files for hygiene, NOT because they crash.

Source: Verified by reading `tests/test_bubble_shield.py:16` + `tests/test_charge_shot.py:7` + `tests/conftest.py` — each cut-only test has its own helper, and the surviving helpers in mixed tests follow the same `**overrides` pattern.

### Anti-Patterns to Avoid

- **Splitting Plan 03 into 6 commits (schema + 5 presets).** Creates a bisect window where schema disagrees with presets and `set_value` either silently passes via forward-compat OR raises mid-game depending on the order. CONTEXT Specifics line 221 already locks this; this research reinforces.
- **Running pytest mid-strip (between Plans 01-04).** Cut-only test files still on disk would either fail (because the surrounding code is gone) or pass (because they test code that hasn't been deleted yet) — neither is signal. Pytest at end of Plan 05 only.
- **Deleting `slime.reposition()` aggressively in Plan 02 without checking callers first.** PATTERNS leaves this to planner discretion (Cross-Cutting Invariant #10). This research recommends DELETE — see Risk Surface 5 below — but only after a final grep confirms no surviving call sites.
- **Touching event subscribers in `Game.__init__`.** Phase 31 contract. Memory `project_reanimator_anim_architecture` enforces. The cut-ability code emits events (e.g., `event_bus.emit("ram_start")`) which exit naturally with their containing methods; subscribers never need to be touched because no Phase 31 subscriber listens for cut event names.

### Sampling Rate (Nyquist mapping)

This is the first-class addition this research makes. CONTEXT D-18 lists four gates as a phase-gate. Nyquist Dimension 8 requires sampling at the *task* and *plan* boundaries, not just the phase boundary. Mapping:

| Boundary | Sampler | Rationale |

| **Per task commit** (within a plan) | `python -c "import src.entities.player; import src.entities.slime"` (~0.5s) | Catches NameError / AttributeError immediately when a half-stripped symbol leaks. Critical during Plan 01 (D-17 sub-steps). |
| **Per plan commit** (Plans 01, 02, 04) | `python main.py` boots to title + Ctrl-C (Gate G2 partial) | Confirms the strip didn't break LDtk load, save load, default preset load, or room 0 render. ~5s. |

## Risk Surfaces (deletion-phase specific)

This is the second new analysis layer. Code-strip risks differ from feature-build risks. Each is paired with a detection step.

### Risk 1: Dead-reference window between Plan 01 and Plan 03

**What goes wrong:** Plan 01 deletes `start_dash` / `apply_dash_physics`. Inside those methods, `tuning.DASH_IFRAMES` is read at use-site (`player.py:136`, `player.py:616`). When the methods are deleted, the reads exit with them — so there's no live code referring to `tuning.DASH_IFRAMES`. But the schema still defines `dash` group keys until Plan 03. This is a **dead reference window**: the symbol is unreachable but resolvable.

**Why it happens:** Plans 01 and 03 are sequential, not atomic.

**How to avoid:** No action needed. CONTEXT D-25 explicitly flags this for awareness. The window is harmless — `tuning.DASH_IFRAMES` resolves to a real number; nothing dereferences it. Closes when Plan 03 lands.

**Detection:** None required.

**Confidence:** HIGH. Verified by re-reading PATTERNS Cross-Cutting Invariants section + Shared Patterns "Tuning-attribute access at use-site."

### Risk 2: Trailing-comma bugs in JSON rewrites (Plans 03, 04)

**What goes wrong:** JSON does not permit trailing commas. When the LAST key in a group is deleted, the previous key's trailing comma must also be removed. Easy to miss; produces `json.JSONDecodeError` on the next load. PATTERNS specifically calls out:
- `gates`: removing `BOOST_CRACKED_V_COST` makes `DRILL_CRACKED_V_COST` the new last entry; its trailing comma must go.
- `fusion`: removing `HOLD_TAP_THRESHOLD` requires the previous key (`SPIT_HOLD_THRESHOLD` per the post-strip key order) to lose its trailing comma.
- `entity-schema.json`: removing `ShieldT2` (the last cut entity) makes `MissileTank` or whatever follows it the new last entry.

**Why it happens:** JSON authoring is hand-driven; no compiler enforces the rule.

**How to avoid:**
1. Validate every JSON file post-edit with `python -m json.tool < file.json` (must exit 0).
2. Plan 03's per-task verify step must include this validation.
3. Plan 04's entity-schema task must include it.

**Detection:** `python -m json.tool < <file>` on every edited JSON file as part of the per-task verify step. Confirm Plan 03 commit includes 6 successful validations (schema + 5 presets); Plan 04 includes 1 (entity-schema).

**Warning sign:** Game boot fails immediately with `json.JSONDecodeError` traceback citing the schema or a preset.

**Confidence:** HIGH. JSON specification, no exceptions.

### Risk 3: Orphan `slime.reposition()` method post-strip

**What goes wrong:** `slime.reposition()` (slime.py:103-137) is the helper called by the deleted player.py:333-339 `was_tap` Hold input branches. After Plan 01 strips those branches and Plan 02 strips Hold state, `reposition` has zero callers in `src/`. Verified by grep 2026-04-26: only 3 hits in `src/`, all in `slime.py` itself (definition at line 103, no callers).

**Why it happens:** PATTERNS Cross-Cutting Invariant #10 explicitly leaves the deletion of `reposition` to "planner discretion." CONTEXT is silent. The conservative reading is "leave it as dead-but-harmless code"; the aggressive reading is "delete it because dead code is technical debt."

**How to avoid:** **Recommendation: DELETE in Plan 02.** Reasons:
1. Phase 31.5's whole purpose is to give Phase 32 a clean base. Leaving an orphan method violates that intent.
2. The method body uses `HOLD_SCAN_RANGE` (a local-scope constant per PATTERNS) which itself is being deleted. If `reposition` stays, a local `HOLD_SCAN_RANGE = 4` either stays inside (orphan constant) or the method body becomes unreferenced anyway.
3. Memory `feedback_magic_numbers` argues against a method whose only constant is local-scope and orphan.
4. The associated test `test_tap_reposition.py` is already being deleted per D-07.

**Detection:** Add to grep checklist: `grep -nE 'def reposition\b' src/entities/slime.py` returns 0 matches post-Plan-02.

**Caveat:** If the planner finds a non-obvious caller (e.g., debug overlay, dev tool, save format reader) during Plan 02 task design, escalate as an open question rather than deleting blind.

**Confidence:** MEDIUM (planner discretion, not locked).

### Risk 4: Test-fixture `make_player(has_dash=False, ...)` post-strip behavior

**What goes wrong:** `tests/test_input_remap.py:70` calls `make_player(has_drill=True, is_grounded=False, has_dash=False, ...)`. Each test file's `make_player(**overrides)` helper applies kwargs via `setattr`. After strip, `setattr(player, "has_dash", False)` SUCCEEDS — Python silently creates a new attribute. The test then proceeds with `player.has_dash == False`, which is technically true but semantically meaningless because no method reads it.

**Why it happens:** Python dynamic attribute model. `setattr` doesn't enforce schema.

**How to avoid:**
- For Plan 05 test cleanup, drop dead kwargs from the 6 mixed-test files for **hygiene**, not because they crash.
- Verify per-file: read each `make_player` helper, identify dead kwargs, strip them.
- If `make_player` helper itself accepts explicit named parameters (not `**overrides`), the unrecognized kwarg WOULD raise `TypeError`. Verified across the 6 mixed test files: each uses `**overrides` pattern, so this is hygiene not blocker.

**Detection:** After Plan 05, `grep -nE '\bhas_(dash|shield|shield_t2|boost)\s*=' tests/` returns 0 hits.

**Warning sign:** `TypeError: __init__() got an unexpected keyword argument 'has_dash'` — would only fire if a helper used explicit params instead of `**overrides`. Did not observe in any of 6 mixed files.

## Deletion-Style Precedents in This Project

This is the fifth analysis layer. The project has stripped code before. What did it do? What broke?

### Precedent 1: Phase 30 cut #2 — Hold mechanic deferred

**What happened:** Phase 30 LOCKED `FUSION-DESIGN.md` with a "cut abilities" enumeration that listed Directional Hold as cut. But the actual code-strip was NOT done in Phase 30 (Phase 30 was design-only). The Hold code remained in `slime.py` and `player.py` from v1.1 onward.

**What broke:** Nothing functionally — the code stayed and worked. But it created the need for Phase 31.5 itself, because Phase 32 cannot start a fusion refactor with stale ability code in the surface area.

**Lesson for 31.5:** The strip MUST land before Phase 32. Don't defer "easy" deletions on the theory that "it still works." `feedback_worktree_regression` and `feedback_push_before_worktrees` both stem from regressions that crept back in via ambiguity about what was supposed to be gone.

**Source:** ROADMAP 2026-04-24 entry inserting Phase 31.5; CONTEXT D-06 spelling out Hold strip in detail; PATTERNS test_tap_reposition.py confirmation.

### Precedent 2: Phase 30 lock dance (3-commit and re-lock cycle)

**What happened:** Phase 30 used a 3-commit lock dance: write doc with `locked_commit: TBD`, commit, amend frontmatter with the real SHA. When the design changed (DOWN+V → DOWN+SPACE), a new 3-commit cycle: unlock → content → re-lock.

**What broke:** Two re-lock cycles needed (cycles 1 and 2) before the design stabilized. Each re-lock involved frontmatter updates + verification re-runs.

**Lesson for 31.5:** Phase 31.5 has NO frontmatter or commit-SHA contract — it's a code strip, not a design lock. But the *acceptance discipline* (gate-by-gate verification with explicit pass/fail) carries over. `31.5-VERIFICATION.md` should follow `30-VERIFICATION.md` structure: list each gate with status + evidence.

**Source:** `30-VERIFICATION.md` cycle-2 section; `30-VALIDATION.md` Per-Task Verification Map structure.

### Precedent 3: `test_kick_removal.py` — testing for absence

**What happened:** A previous strip phase removed the kick mechanic and added `test_kick_removal.py` as a regression test that asserts kick artifacts are gone (file-content greps and routing assertions).

**Lesson for 31.5:** Could write `test_cut_abilities_removed.py` mirror, but **CONTEXT D-24 explicitly forbids** `assert "has_dash" not in saved` style regression tests because Phase 32's `version: 2` save bump will supersede them. The grep-checklist gate (Gate 1) IS the tested invariant, run from a shell command not from pytest.

**Source:** `tests/test_kick_removal.py` exists in the test tree (verified by directory listing); CONTEXT D-24 explicit forbiddance.

### Precedent 4: `test_goo_mold_removal.py` — same pattern

**Source:** `tests/test_goo_mold_removal.py` exists. Same lesson as Precedent 3.
